# Notes on the 2026-11-01 run

Read alongside [`2026-11-01.md`](./2026-11-01.md), which holds the tables, and
[`2026-11-01.json`](./2026-11-01.json), which holds every sample. The previous run
is [`2026-10-01`](./2026-10-01-notes.md); every `head` and `base` pin is the same in
both, and `init` detected the same plugins on all nine, so the counters compare
directly.

Environment: 4 vCPU Intel Xeon Platinum 8573C, 16 GiB RAM, Linux, **Node v24.22.1**,
`aburi` 0.5.0 built from `ceaa9240` (clean) by the `Benchmark` workflow. Last month
was an AMD EPYC 7763 on Node v24.21.0, so the runner changed again and the cost
columns cannot be read across the two runs on their own.

## Both runs reproduce exactly, so every counter move is accounted for

The results file now records the Aburi commit it measured, so this time nothing had
to be reconstructed: 10-01 measured `3b917f21`, 11-01 measured `ceaa9240`.

Both were rebuilt and swept again on one machine (4 vCPU Xeon @ 2.10 GHz, Node
v24.22.1). On all nine repositories, both builds wrote an IR byte-identical to the
one CI wrote, hash for hash. Counters carry across runners exactly, not only roughly.

Every commit between the two that touches scan-side source (core, lang-typescript,
the framework plugins, cli, config, plugin-registry, types) was then built and
scanned over all nine pins, 74 builds in order. The first reproduces the 10-01
counters and the last the 11-01 counters, so the tables below account for each move
in full.

## Cost: the code got slower, and the new runner hid part of it

Same machine, two interleaved sweeps per build, median of six measured scans:

| Repo | CI 10-01 → 11-01 | Same machine, `3b917f21` → `ceaa9240` | Diff, same machine |
|---|---:|---:|---:|
| `zustand` | 0.34 → 0.34 s (−0%) | 0.27 → 0.27 s (**−1%**) | noise at this size |
| `express` | 0.50 → 0.49 s (−2%) | 0.40 → 0.40 s (**+1%**) | noise at this size |
| `hono` | 1.88 → 2.02 s (+7%) | 1.46 → 1.58 s (**+8%**) | 2.90 → 3.45 s (+19%) |
| `zod` | 2.65 → 2.91 s (+10%) | 1.99 → 2.39 s (**+20%**) | 4.08 → 5.40 s (+32%) |
| `trpc` | 2.08 → 2.36 s (+13%) | 1.61 → 1.94 s (**+21%**) | 3.39 → 4.24 s (+25%) |
| `tanstack-query` | 3.39 → 3.47 s (+2%) | 2.52 → 2.98 s (**+18%**) | 5.58 → 6.63 s (+19%) |
| `shadcn-ui` | 10.37 → 13.01 s (+25%) | 8.14 → 10.97 s (**+35%**) | 17.15 → 23.40 s (+36%) |
| `nest` | 3.67 → 3.81 s (+4%) | 2.83 → 3.25 s (**+14%**) | 6.21 → 7.47 s (+20%) |
| `cal-com` | 13.48 → 15.17 s (+13%) | 10.43 → 12.85 s (**+23%**) | 23.27 → 26.75 s (+15%) |

On one machine the scan slowed **+8% to +35%** on every repo past 300 files, where
the CI table shows −2% to +25%. The gap between the two columns is 8–16 points on
six of the seven larger repos (1 on `hono`) and nil on the two smallest: the new
runner's gain grows with the workspace, and it hid between a third (`shadcn-ui`) and
nearly all (`tanstack-query`) of the slowdown. `trpc`'s +21% includes 10% more files
(see below); per file it slowed about 10%.

**One commit is the largest share.** The 74-build series showed three steps; each was
measured again over five interleaved rounds against the build before it:

| Commit | `zod` | `shadcn-ui` | `cal-com` |
|---|---:|---:|---:|
| `128b9e6` Keep operators, keywords and modifiers in the syntax fingerprint (#415) | **+7.5%** | **+17.6%** | **+15.5%** |
| `d23fc40` Give the functions an object literal holds Symbols of their own (#427) | −3.2% | +1.3% | +1.3% |
| `b7402a3` Describe a function's parameter list in its syntax string (#526) | +1.3% | +0.3% | +2.1% |

`128b9e6` is half to two thirds of the whole slowdown on `shadcn-ui` and `cal-com`,
and about 40% on `zod`. The rest is creep across the other sixty-odd commits, none
above the ±5% a single run moves on its own.

**The hotspot is `normalizeAst`.** A CPU profile of one `shadcn-ui` scan puts it at
0.94 s of 9.4 s on `3b917f21` and **2.84 s of 12.1 s** on `ceaa9240`, while
`parse` stays at 2.1–2.2 s. Since `128b9e6`, `serialize` walks `node.children`
instead of `namedChildren`, and each child is asked `isMissing`, `isNamed` and
`isExtra` (twice for a token), its `type` three or four times, and its parent's
`type` once more. In web-tree-sitter every one of those getters marshals the node
and crosses into WASM, and `children` allocates a `Node` for every anonymous token. The profile's top
self-time entries under it are web-tree-sitter's `Node` constructor and
`marshalNode`.

A prototype that reads each child's `type` and flags once and passes the parent's
type down writes **byte-identical IR on all nine repositories** and passes the
lang-typescript suite. It measures **−7.2% `zod`, −6.6% `shadcn-ui`, −4.3% `cal-com`**
(four interleaved rounds). On `shadcn-ui` and `cal-com` that is a third to a half of
what `128b9e6` cost; on `zod` it is more than all of it, since the walk before it
already asked for `type` several times per node. Most of what remains is the `Node`
allocations, which a `TreeCursor` walk avoids. The cursor does not expose
`isExtra`, so that version needs a decision about how extras are told apart.

**Diff** cost tracks scan cost: on the seven larger repos `diff` stays at 2.0–2.3×
a scan on both builds. `zustand` and `express` are too small to read. One build gave
1.03 s and 0.54 s for the same `zustand` diff in two sweeps.

**`init` −15% to −38%** on CI is the runner. On one machine the two builds' `init`
times match (e.g. `cal-com` 344 / 337 ms).

**Peak RSS** is multi-modal, so read single moves with care. `tanstack-query`'s
+26% on CI (241 → 304 MiB) is not the code. Across the 74 builds its scan sits at
≈240 MiB or ≈290 MiB, flipping between consecutive commits that leave its
counters unchanged (`50c0bd2` 290, `eb4ab00` 240; `90fa1cb` 296, `107c1c6` 239). Every
other scan moved within ±5%. The high-water mark is `cal-com`'s diff at 955 MiB,
down from 965 MiB and still under half of the 2 GiB budget.

## Counters: what moved, and which commit moved it

### Resolution

| Commit | Effect |
|---|---|
| `8187694` Resolve relative imports written with an emitted extension, `.` or `..` (#409) | `nest` resolved **212 → 781**, deps 159 → 686; `zod` resolved **+525**, deps +428; `tanstack-query` +73 |
| `568ab0c` Answer the computed segment for a callee receiver that is not a name (#410) | `noMatch` → `dynamic` on all nine (`cal-com` +499, `shadcn-ui` +367, `zod` +125); totals unchanged |
| `dfffac9` Let a destructuring parameter's bindings shadow outer names (#447) | `noMatch` and `dynamic` → `localScope`: `cal-com` **+1,815**, `shadcn-ui` +446, `tanstack-query` +180 |
| `3b52db9` Resolve a call through a default import to the default export (#446) | resolved `cal-com` +18, `zod` +3 |
| `0f48301` Read a receiver behind a type assertion without its type (#520) | `dynamic` −7 to −28 into `noMatch` / `localScope` |

**`nest`'s 2.2% was mostly an import resolver gap, not dependency injection.** NestJS
writes its relative imports ESM-style, `from './injector/instance-wrapper.js'`, and
those missed the `.ts` source. `8187694` took `nest` from 2.2% to 8.0% on its own,
and the 09-01 and 10-01 notes' reading should be corrected. Constructor-injected
receivers are what remains (`dynamic` is still 37% of `nest`'s calls). The most
common newly resolved callees are `HttpException.createBody`,
`HttpException.extractDescriptionAndOptionsFrom`, `isString` and `isFunction`.
`zod` v4 imports the same way (`util.joinValues`, `util.normalizeParams`,
`addIssueToContext`), which is most of its 20.2% → 29.0%.

### Calls: the denominator grew, and on `shadcn-ui` most of it is generated code

| Commit | Effect |
|---|---|
| `d23fc40` Give the functions an object literal holds Symbols of their own (#427) | calls `shadcn-ui` **+15,609**, `cal-com` +1,074, `tanstack-query` +270; Symbols +472 across the nine (`cal-com` +233) |
| `f17849d` Walk calls in catch and finally blocks (#438) | calls `cal-com` +1,137, `shadcn-ui` +213, `nest` +131, `trpc` +91 |
| `bf2498f` Walk the functions a call-initialised const hands its call (#417) | calls `cal-com` +773, `shadcn-ui` +710, `trpc` +609 |
| `600c801` Give a class field holding a function handed to a call a member Symbol (#524) | `tanstack-query` calls +107, Symbols +34, dropped 745 → 728 |
| `56798c7` Read a generator function as a function at every site (#518) | `hono` calls +28 |

**`shadcn-ui` calls +80% and resolved 9.5% → 6.3% is 37 generated files.**
`apps/v4/{examples,registry}/**/__components__/*.tsx` and the three `__index__.tsx`
open with "This file is autogenerated" and hold one object each:

```ts
export const Components: Record<string, any> = {
  "accordion-basic": React.lazy(async () => {
    const mod = await import("@/examples/base/accordion-basic")
    const exportName = Object.keys(mod).find(…) || "accordion-basic"
    return { default: mod.default || mod[exportName] }
  }),
  …
```

A quoted key mints no member Symbol, so since `d23fc40` the binding carries every
entry: `examples/__components__/base.tsx#Components` alone holds 2,052 calls
(`React.lazy`, `import`, `Object.keys`, `Object.keys.find`, 513 times each). Those
37 files hold **15,485 calls, none resolvable**. Leave them out and `shadcn-ui`
resolves **10.9%**, up from 9.5%. A closure inside a body is read as part of that
body everywhere else too, so this is not an extraction bug. But generated files now
decide the headline resolution rate of the largest React repo here, and the
function inside `React.lazy` runs when the component first renders, not when the
object is defined. Excluding generated files,
or reporting them apart, is the decision this raises.

Cost is not where this lands. `d23fc40` measured +1.3% on `shadcn-ui` (table above).

## Caveats

- The CI numbers are one run per repo on each of two different runners. The
  same-machine figures are two sweeps per build, three measured scans each, on a
  4 vCPU cloud VM whose single runs move ±5%.

  timings were only used to choose the three commits re-measured over five rounds.
- The profile is one sampled scan per build of one repository (`shadcn-ui`).
